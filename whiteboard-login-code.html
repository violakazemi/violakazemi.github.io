Login Code: ending the resend loop

A waiting state for the security code step of a banking app, based on a real app store review.

FormatWhiteboard exercise
PlatformNative mobile
DateOctober 2026

The prompt

A real app store review of a Canadian banking app. The reviewer says the app asks for a text code at every login, the “Remember me” box seems to do nothing, and he has to tap resend four or five times before a code arrives. He is shopping for another bank. I renamed the bank Cherry and changed its colours.

Diagnosis before design

The reviewer wrote that the code “never sends the first time.” I separated what he saw from what he concluded. He saw that he tapped, no code came, he tapped again several times, and then a code came. He concluded that the first one was never sent. From his side of the screen he has no way to know which tap produced the code that arrived.

That left two places where the problem could be.

  • Between his tap and our handoff to the SMS provider. Nothing on screen tells him a request is in progress, so he taps again. If each tap sends a new code and cancels the previous one, his own tapping is part of the failure.
  • Between the handoff and his phone. The carrier is slow or drops the message. No screen change fixes that.

I would check the send logs before designing: one message per tap, and whether each was delivered or failed. I would look at the carrier side first, because that fix sits outside the app team and it is the most expensive answer to find out late.

A waiting state for Cherry clients who can't log in, to end the repeated tapping caused by no feedback between the tap and the handoff.

I deliberately left the carrier delivery problem to the SMS provider team.

One user, one situation

  • Ali is at home at 11:50pm. He just remembered his electricity bill.
  • He has ten minutes before a late fee.
  • He is on good wifi with a full signal. I chose that on purpose: if the code still takes four taps, the cause is on the app side, which is the problem I committed to.

Pain points and priorities

The flow

  1. He opens the app. His Login ID is already filled in, because “Remember me” is on by default.
  2. He enters his password and taps “Send security code.”
  3. The waiting state starts: the screen says where the code was sent, a 30 second countdown runs, and resend is locked.
  4. If the code arrives, the app fills it in. He is logged in and pays the bill.
  5. If 30 seconds pass with no code, the screen says so and resend unlocks. He taps it and the waiting state starts again.
  6. After a second timeout, the screen offers a phone call or an email, so he is never stuck.

The key screens

  1. Log in. One primary action. The button names what happens next: “Send security code.”
  2. Waiting. The largest element is the “Code sent” card with the live countdown, because that reassurance is what stops him tapping. The locked button shows three signals and never colour alone: a muted fill, new text (“Resend in 0:24”), and a spinner.
  3. Timeout. The card changes to “The code didn't arrive” and the button returns to full colour with “Resend security code.” It also tells him the first code will stop working.

Three questions I had to answer

  • Why lock the button when he is in a hurry? Every extra tap may send a new code and cancel the previous one, so the tapping is part of what breaks the login. The lock protects his request, and the countdown tells him it is working.
  • Why 30 seconds? It is a starting assumption, because most carriers deliver a text within that window. I would set the real number from our delivery data. If 95% of codes arrive within 20 seconds, the countdown becomes 20.
  • Is the call or email option out of scope? Delivering the text is the carrier's job. Not leaving Ali stuck when it fails is a design job, so it stays in.

Edge cases

  • His phone storage is full and the text cannot arrive. After the second timeout he can get the code by phone call or email.
  • The text is never delivered. The same second route gets him in tonight. The delivery failure goes to the SMS provider team.
  • He cannot type or copy the code. The app reads the incoming text and fills the code in, and “Paste code” sits beside the field.

How I would know it works

The share of login attempts that end in a successful login within two minutes of the first code request.

What I would do differently

  • My first attempt opened with the solution, a disabled state for the button, before I had asked whether the code was being delivered at all. I redid the exercise starting from the cause.
  • My first metric was taps per login. A locked button forces that number down even if nobody logs in faster, so I replaced it with a number my own design cannot fake.
  • I left out “a code at every login” as a security rule. The bank's help centre describes a trusted device setting that skips the code. If the reviewer never found it, that is a discoverability problem, and it is the next thing I would take on.
  • Next I would tune the 30 seconds against real delivery times.

The screens were drawn with Claude from my design decisions. Cherry is a made-up bank, and the Login ID and phone number are sample data.
