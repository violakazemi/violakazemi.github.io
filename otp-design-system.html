One Design System, Two Bank Apps

One set of tokens and 14 components, so each bank could look like itself without breaking anything.

RoleUI/UX Designer
CompanyCarrene Corp
Timeline2023 – 2024
PlatformsiOS & Android

My part: I proposed this design system and built it, from the first audit to handoff.

Note: I rebuilt these screens to share them here. The flows and decisions are real.

The short version

I started as the only designer on a team of four. The app had three screens. Then one app became two, every screen had its own colors, and changes got lost. So I built one design system for both apps.

Context and my role

The product was a one-time password app for banks, on iOS and Android. It was B2B2C: the banks bought it, and their customers used it. Every decision had to clear the bank’s security team and still work for someone standing at an ATM. I proposed the design system and built it. Later a second designer joined and worked with the same system.

Why it was needed

It started small

Three screens, no design system. Everyone set their own colors, on every screen.

Then one app became two

The biggest bank wanted the app just for itself, so the other banks moved into a second app. Front-end and mobile work went from 2 developers to 5. With more hands on more screens, the inconsistencies grew.

Then things started to break

The same color had different names: primary_first, primaryFirst, or just a hex code. Developers set colors by hand. QA found 4–5 color bugs in every release.

So I asked for one week

I showed how one system would cut the gaps between the teams. I got one week to prove it. I built the color system first. The team accepted it, and the rest followed.

How I built it, step by step

I rebuilt the system in Figma. Bow Bank is the single-bank app, in green. Elbow Trust holds many banks, in indigo. Every step, token and component below comes from that file.

Step 1

Audit: see everything first

I put every screen from both apps side by side, on iOS and Android. Then I cut out every piece: buttons, inputs, cards, text, colors, icons. I sorted them by type and counted how many versions of each one existed.

  • The same color had different names, or no name at all.
  • One app had no system at all. The other had one of its own.
  • The two apps had 38 components between them, and many were the same part built twice.
Step 2

I checked in two directions. Inside one app: does the app match itself? Between the two apps: is this the same part in a different color?

Step 4

Semantic tokens: names by job

Every primitive gets a job. Components only use these names, never a primitive.

The first version followed Material’s role names, like primary and on-surface. That gave the team one language, and iOS used the same names as Android. But the audit showed two problems. The hex codes were typed straight into those names, with no primitives under them. And two names did the same job: background and surface were both white.

So I put the primitives underneath and grouped the names by job: text, surface, border, brand, feedback. background and surface became one name, surface/default, and the light grey behind controls kept a name of its own, surface/subtle. Two names doing one job became one name with one job.

Step 5

Component tokens: only where needed

Most parts use semantic tokens directly. Three get their own: Button, Code card and Timer. The test is not whether a part changes per bank or per platform — nearly all of them do, and a semantic token already carries that. A part earns its own tokens when the token it points to changes. The Code card’s digit points to text/primary in Bow Bank and brand/primary in Elbow Trust. One semantic name cannot hold two different pointers, so the Code card gets its own.

The other eleven parts never do this. The Segmented control’s label is 13 on iOS and 14 on Android, but it always points at type/segment-label. Same pointer, different value — so it needs nothing of its own. A button never asks for a color. It asks for a job.

  • The tap area is built into the component: 44 on iOS, 48 on Android. The visible part can be smaller — an Android button is 40 tall, centered in a 48 tap area.
  • Platform parts stay native. iOS follows Apple’s guidelines, Android follows Material 3.
  • No component comes from an outside kit. The platform kits stay attached to the file as reference only.
DecisionA borrowed component is easy to miss, because on the canvas it looks like any other instance. I swept the whole file and found one left: a check icon from the Material 3 Design Kit, 18×18, inside the Segmented control’s two Android variants. The Code card and the Code switcher nest that control, so they had inherited it too — one borrowed icon in 11 places. I swapped both Android variants to this file’s own icon/check: an 18 instance with the stroke set to 1.5 and the color on brand/on-subtle. All 11 uses resolve to it now. The iOS variants have no check, so they were not touched. Then I removed the Simple Design System library. iOS and iPadOS 27 and Material 3 stay attached as reference, and no component in the file depends on an outside kit.
DecisionOnly the Android segmented control shows a check on the selected segment. That is Material 3, and on Android it is also the second cue, because the selection is otherwise a green tint. iOS keeps the sliding white pill, which is already a shape cue, so it gets no check. A second cue is only needed where the first one is color alone.
DecisionThe Code card carried a Password 1 / Password 2 tab above the digit boxes, but the tab and the boxes were separate parts with nothing holding them together. The tab could read Password 2 while the row below it still showed the four-digit code. Two independent parts can always disagree, so I merged them into one Code switcher: the tab and the row it controls are the same component, and the digit count follows from which password is selected — four for Password 1, six for Password 2. The Segmented control stays a component of its own, because Elbow Trust uses it on screens that have no code on them.
DecisionThen six digits did not fit. The card was 343 wide — a number traced off a screenshot, not chosen — and six boxes at 56 with a 12 gap come to 396. I set the card to 350, which is what screen-margin 20 leaves on a 390 screen, and let the box width follow the longest code: 56 for four digits, 44 for six, gap fixed at 12 in both. The gap is the token. The box is whatever makes the longest code fit the card, so a seventh digit would not break it.
LessonMeasuring that row found a bug I had not been looking for. The iOS digit boxes were set to hug their contents, so the box holding a 1 was narrower than the box holding an 8 and the whole row changed width with the code. Fixed widths fixed it. A number you can defend is worth more than a number that happens to look right.
Step 7

Theming: one system, two banks

It carries a border token and a shadow token, and each bank sets one of them to none — Bow Bank the shadow, Elbow Trust the border. Same component, same properties, different values. Switch the bank below. The components don’t change. Only the values do.

Tokens go straight to code

The tokens leave Figma as one file. The iOS and Android values are generated from it, so nobody retypes a hex code. When a token changes, the change reaches both apps the same way.

Step 9

Governance: how it stays alive

The rules

Three layers, one direction: component, semantic, primitive. Name by job, not by look. A new value rounds to the nearest step on the scale first. A token is added to both banks or to neither.

How a change shipped

The team lead approved a new component or token before it went in. Each sprint had a planning and tasking day. On that day, a handoff meeting walked the developers through what was new and why.

Before a new component goes in, I ask one question first: can an existing component do this job with a new variant?

Accessibility is built in, not checked at the end

Every rule here lives inside a token or a component, so a screen gets it without anyone remembering to add it.

Contrast is checked per pair

Every text and edge color was checked against the surface it sits on before it became a token. A gray that failed was merged into one that passed.

Small parts still get big targets

The Copy chip is 24 tall and the Android button is 40. Each one carries an invisible tap area around it, so the size that matters lives in the component and not in a reviewer’s checklist.

No state relies on color alone

The selected bank gets a check mark. The active tab gets a bold label or a pill. On Android the selected segment gets a check, because the tint behind it is the only other sign. On iOS the pill does that job. A focused field gets a thicker border and a caret. The timer ring pulses in its last 5 seconds.

Text can grow

The codes and the countdown follow the phone’s text size, and the digit box grows taller with them. Its width is fixed: six digits have to fit a 350 card, so the row is sized for the longest code rather than the largest text.

Step 10

Results

Color bugs went from 4–5 per release to zero

One place for colors, not one per screen. When a color changed, it changed everywhere.

One system ran across both apps

Same names, same components, same flows. Only the values changed per bank.

Another designer built a new theme with it

Later, another designer used the system to make a new purple theme for a redesign. Same names, same components, a new look. That was the real test.

Developers got names, not hex codes

Every screen I handed off pointed to tokens. The whole team spoke one language.

Reflection

Prove it small first

I didn’t ask for a design system. I asked for one week, and I built only the color system. A small thing that works is easier to say yes to than a big plan.

Audit every layer

Never write “nothing” in an audit until you’ve checked every layer. Look at the middle of the screen, not only the frame around it.

One rule is easier to keep than ten

Components only use semantic tokens, with no exceptions. A rule with no exceptions is one engineers can check on their own, without asking me.

Start accessibility in the audit

The first timer showed the last 5 seconds in red only. The pulse came later, for people who can’t tell red apart. Today I’d look for color-only states and small tap areas during the audit, not after.

What I’d improve today

  • Themes as modes. My Figma plan allows one mode per collection, so each bank has its own collection with the same token names. With modes, switching a bank is one click on the frame.
  • Test large text on real phones. The digit boxes now grow with the text. I’d check the Home screen at the largest text size on both platforms.
  • Dark mode. Every color already goes through a semantic token, so a dark theme is a new list of values, not new components.
  • An error state on the Input. feedback/error exists as a token, but no component uses it. A wrong activation code has a color and nowhere to show it, and a system should not carry a token with no home.
  • Screen reader names. I’d write the spoken label for each component into its spec, next to the tokens.
